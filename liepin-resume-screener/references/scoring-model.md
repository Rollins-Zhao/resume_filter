# 四维打分模型详解与调参指南

> 本文以内置的通用销售岗示例模型讲解方法；实际岗位请在岗位画像（profiles/*.json）里覆盖维度与关键词，方法完全一致。

## 一、设计理念

目标：把"资深 HR 看简历时的判断逻辑"编码成可复现的规则，做到**既不误伤（泛泛提及被当成核心经验），也不漏判（真经验被打低分）**。

模型满分 100，四个维度加权（示例模型的划分）：

| 维度 | 权重 | 含义 | 为什么这个权重 |
|---|---|---|---|
| 销售领域 | 30 | 大客户/B2B 销售、渠道/代理销售 | 领域经验直接决定能否上手 |
| 业绩表现 | 30 | 业绩量化、超额完成、销冠 | 结果导向岗位，业绩是最硬的信号 |
| 核心技能 | 25 | 客户开发与谈判、客户关系管理 | 岗位本职能力 |
| 行业背景 | 15 | B2B/企业服务、相关行业 | 行业理解成本，可培养 |

维度键名、个数、权重完全自由（报告的维度列由画像动态生成），按你的岗位重新设计即可——参考 `profiles/example-销售经理.json`。

## 二、两类维度规则

### 上下文维度（如示例中的"业绩表现"）—— 关键机制

**核心机制：规则关键词必须与「上下文词」出现在同一句，才算强命中。**

- 上下文词表（`scoring.performance.contextWords`，示例）：
  `完成 / 达成 / 超额 / 实现 / 取得 / 业绩 / 销售额 / 回款 / 营收 / 增长`
- 分值：业绩突出 = 18；业绩达标 = 12（封顶 30）
- **弱命中**：整篇只泛泛提到关键词但无上下文 → 仅 `weakScore`（6 分）背景分

用途：防止"简历里出现过'目标'二字就给业绩分"这类误报。设计你自己的维度时，
凡是"必须在具体业务语境里才算数"的经验，都适合做成上下文维度。

**分句规则（关键，改错会严重影响准确率）**：

```js
const segs = t.split(/[。；;\n]+/);   // 正确：按句号/分号/换行切
// const segs = t.split(/[。；;\n，,]+/);  // 错误：按逗号切会把关键词拆散
```

中文简历逗号极密集，按逗号切分会导致"负责美国线路，尾程派送管理"这类表述被拆成两段而丢失命中。**必须只在句号/分号/换行处切分。**

### 普通维度（如示例中的"销售领域 / 核心技能 / 行业背景"）

按规则命中累加，封顶 `weight`；一条都没命中给 `other`（通常 0）。

> 实测提醒：部分简历用同义词或英文缩写（如"大客户"写作"KA"、"key account"）。如遇漏判，在对应 `rules[].keywords` 里补充别名即可。

## 三、分级阈值

| 等级 | 分数 | 含义 |
|---|---|---|
| S | ≥ 80 | 强匹配，优先触达 |
| A | ≥ 60 | 匹配，建议触达 |
| B | ≥ 40 | 部分匹配，备选 |
| C | < 40 | 不匹配 |

`minReportGrade` 控制报告入表门槛，**默认 `"C"` = 全量收录**（v2.9.1 起，用户拍板「报告不要门槛，都放进来」；旧默认 "A" 会把 B/C 挡在报告外）。想收紧可钉 `"A"`/`"S"`。

## 四、如何校准你的模型（代替照抄别人的阈值）

新岗位跑完第一轮后，用 10-20 份人工复核过的简历做一次校准：

1. **跑分**：`node "<skill>/scripts/show-scores.js"` 看每份的维度得分与命中标签。
2. **对人工判断**：把"你觉得该进面 / 不该进面"的人与 S/A/B/C 对照。
3. **修误报**：好人分数偏低 → 缺关键词（补同义词、英文别名）或上下文词表太窄。
4. **修漏判的镜像（误报）**：差人分数偏高 → 某条规则关键词太泛（拆细、降分），或该维度应改成上下文维度。
5. **改完零网络重算**：

```bash
node "<skill>/scripts/screener.js" rescore   # 基于本地简历缓存重算，不发任何请求
```

虚构示例（仅供理解格式，非真实数据）：

- 某制造业大客户销售 —— 85 分 S（领域 15 + 业绩 30 + 技能 25 + 行业 15）
- 某零售店长 —— 42 分 B（领域 0 + 业绩 12 + 技能 25 + 行业 0），行业不符，正确压低

## 五、调参指南

### 换岗位时改什么

优先改**岗位画像**（不要改 skill 内默认值，便于多岗位并存）：

1. `keywordGroups` —— 搜索关键词组（每组一条 `search` 命令）
2. `scoring` 各维度的 `rules[].keywords` 与分值
3. 上下文维度的 `contextWords` —— 该岗位的业务语境词
4. `greetTemplate` —— 话术模板（供用户复制，脚本不发送）

### 提高/降低严格度

| 目标 | 调整方式 |
|---|---|
| 更严（减少误报） | 缩小 `contextWords`、拆细关键词规则、提高 `gradeBands` 分数线 |
| 更宽（减少漏判） | 扩充 `keywords`（加中英文别名、同义词）、增加 `contextWords`、降低分数线 |

### 排查单份简历为何得分异常

```bash
# 查看全部评分明细
node "<skill>/scripts/show-scores.js"

# 从缓存里直接看某份简历的原文（定位关键词命中情况）
cat data/resumes/<resume_id>.json
```

## 六、数据文件说明

| 文件 | 用途 |
|---|---|
| `data/resumes/<id>.json` | 简历全文缓存（含 `text` 原文、`search` 原始字段、`fields` 摘要）——支持零网络重算 |
| `data/processed.json` | 已处理候选人去重库（增量扫描时只碰新简历，防重复消耗请求配额） |
| `data/denied.json` | 无权限/不存在的简历（跳过且不重试，避免浪费请求） |
| `data/quota.json` | 当日请求计数（单日上限见 config） |
| `data/last-results.json` | 最近一次评分结果（报告脚本的数据源） |
| `recommended-index.json` | 推荐去重索引：已进过推荐报告的候选人（同一岗位同一人只推荐一次；详见 SKILL.md「推荐去重」） |
| `logs/run-<date>.log` | 每条 liepin 命令的完整输入输出（可追溯、可取证） |
