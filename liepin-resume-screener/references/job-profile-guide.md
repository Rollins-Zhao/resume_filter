# 岗位画像指南（多岗位切换）

## 〇、形式 0：报岗位名直连（最省事，优先尝试）

用户只报岗位名（如「我在招销售经理，帮我筛」）→ 先查已发布岗位再起草画像：

**【硬性前置，任何形式都一样】生成画像前必须确认 `profiles/_user.json` 存在**；不存在 → 先问公司名/行业/业务方向/常用城市四项并确认写入（见 SKILL.md「用户背景档案」节），再继续。

1. 跑 `node "<skill目录>/scripts/joblist.js --json"` 读平台在招岗位（退出码 2=先引导登录；5=格式未适配/列表拿不到 → 直接降级到形式 1，不阻塞）。
2. 匹配（与 run.js matchProfile 同款）：精确名称 → 唯一子串；未命中/多个 → 列出在招岗位让用户挑；确实没有 → 降级到形式 1。
3. 命中 → 起草画像：`jobTitle`=岗位名、`city`=列表城市（缺省取 `_user.json` commonCities → 北京）、`project` 缺省留空（自动取档案公司名）、`greetTemplate` 用 `我们是{company}`；**scoring 用内置默认并在 `_说明` 注明建议定制**。
4. **列出要点等用户确认后再跑**（确认即跑，不多问）。

## 一、用户如何提供岗位要求 —— 三种形式，任选其一

> **存放位置（重要）**：岗位画像一律存放在 skill **外部**的 `profiles/` 目录（通常与 skill 文件夹同级）。skill 包内不含任何岗位数据——这样无论有多少个岗位，工具包都保持通用；移动整个项目文件夹即可迁移。

### 形式 1：直接对话描述（最推荐）

用户只需自然语言描述岗位，AI 按本文档规则生成 `profiles/<岗位名>.json`，无需用户碰代码。

**生成画像前先读用户背景档案 `profiles/_user.json`**（按 JOB_PROFILE 同款路径查找；不存在则先向用户问一次公司/行业并生成档案）：
- `project` 默认取档案的 `companyName`（用户画像里显式写了 project 则画像优先）
- `greetTemplate` 用 `我们是{company}` 占位符——公司名自动跟随档案，用户改档案即全局生效
- `scoring.industry` 维度的种子词参考档案的 `industry` / `businessSummary`
- 画像 `city`/`cities` 缺省时建议档案的 `commonCities`

> 用户示例：
> 「我要招一个**销售经理**，北京和上海都要，要求有 B2B 大客户销售经验，业绩突出，会商务谈判，最好来自企业服务行业。」
> （有档案时用户不必再说明"我们是谁"；无档案时顺带问一句公司/行业，确认后写入 `profiles/_user.json`——旧值追加进 history）

AI 生成画像后，运行：

```bash
JOB_PROFILE="profiles/销售经理.json" node "<skill目录>/scripts/screener.js"
```

（推荐普通用户直接双击项目根的 run.bat，会自动列出让选。）

### 形式 2：填写模板

复制 `profiles/_template.json` 改名填写（字段带中文说明）。适合结构清晰、想自己掌控打分的用户。

### 形式 3：复制已有画像

`profiles/example-销售经理.json` 是填好的完整示例，可作为同类岗位的起点。

## 二、AI 转换规则（自然语言 → 画像字段）

### 字段映射

| 用户描述中的内容 | 映射字段 |
|---|---|
| 岗位名称 | `jobTitle` |
| 项目 / 公司名 | `project`（缺省取 `_user.json` 的 companyName；画像显式写=覆盖，多项目场景用） |
| 工作城市 | `city`（单个）；多个城市用 `cities` 数组（run.bat 会逐城跑） |
| 必须项、加分项中的技能词 | `keywordGroups` 搜索词 + 对应维度 `rules[].keywords` |
| 必须在同一语境出现的经验（如"在某业务里做过某事"） | 做成**上下文维度**：维度里写 `contextWords` + `rules` + `weakScore` |
| 岗位日常职能 | 职能类维度（如 `skills`）的 `rules` |
| 目标行业背景 | `industry.rules`（**用户说"这个岗位不限行业/跨行业招"时按用户要求写画像，不硬套档案的行业**；档案行业只是未提时的种子词） |
| 年龄上限 / 最低学历 / 必须命中的维度标签 | `reportFilters`（报告层硬筛：`ageMax` / `minDegree` / `requireDimHits`） |
| 同一人是否允许重复推荐 | `allowDuplicateRecommendations`（默认 false，同一岗位只推荐一次） |
| 该岗位当天最多浏览多少份简历 | `dailyResumeQuota`（可选；默认按"全局剩余 ÷ 岗位画像总数"均分，全局每平台每日 1000 份硬顶） |
| 打招呼语气、卖点 | `greetTemplate`（占位符 `{dim1}`..`{dimN}`、`{company}`=档案公司名，或 `{维度label}`） |

> 维度键名（region/carriers/dispatch 之类）完全自由，报告列名取 `label`。本文示例用销售岗的四维：`domain` / `performance` / `skills` / `industry`。

### 四维填充顺序（必须按此顺序追问，缺失就向用户确认）

以销售岗示例为例（其他岗位按同样思路换维度含义）：

1. **领域经验** → 领域类维度 `rules`：问"候选人最好做过哪类业务/市场"
2. **业绩语境** → 该维度的 `contextWords`：问"什么词能证明他真做成过"（把成果词与语境词连成一句才算强命中）
3. **核心技能** → 技能维度 `rules`：问"他每天主要做什么事"
4. **行业背景** → `industry.rules`：问"从哪个行业出来的候选人最合适"

### 关键词组生成原则（3–6 组）

- 每组 2 个词、空格分隔（猎聘搜索为"与"关系）
- 组间要有区分度，覆盖不同切入角度：
  - 职能 + 行业：`销售经理 B2B`
  - 对象 + 动作：`大客户销售`
  - 渠道 + 类型：`渠道销售`
  - 方案 + 类型：`解决方案销售`

### 打分权重建议（可覆盖 `weight`）

| 岗位类型 | 领域/资源 | 业绩/结果 | 职能/技能 | 行业 |
|---|---|---|---|---|
| 资源型（渠道/采购/BD） | 35 | 25 | 25 | 15 |
| 结果型（销售/增长） | 25 | 35 | 25 | 15 |
| 管理型（总监/负责人） | 25 | 25 | 25 | 25 |

> 维度权重总和建议保持 100，便于跨岗位比较分数。

### contextWords 专题：防"泛提即得分"（2026-10-27 真机实证）

不配 `contextWords` 的维度 = **全文子串匹配**：关键词出现在任何位置（包括自我评价、求职意向）都算命中拿分。真机跑 BOSS「数据分析师」岗位（4 个维度全没配 contextWords）时，有候选人的治理分来自自我评价一句「具备数据质量保障意识」——**这是立场，不是经历**。

配上 `contextWords`（动作/语境词）后，关键词必须与其中任一词**同句**才算强命中；全文有关键词但无同句 → 只得 `weakScore`：

```json
{
  "数据治理": {
    "weight": 20, "weakScore": 5,
    "contextWords": ["负责", "搭建", "建设", "落地", "优化", "主导", "推动"],
    "rules": [
      { "label": "治理体系", "keywords": ["数据治理", "数据质量体系"], "score": 10 },
      { "label": "质量工具", "keywords": ["元数据", "数据标准"], "score": 10 }
    ]
  }
}
```

| 简历表述 | 无 contextWords | 有 contextWords |
|---|---|---|
| 「负责公司级数据治理平台的搭建与落地」 | 满分 | 满分（强命中） |
| 自我评价「具备数据质量保障意识」 | 满分（**误报**） | 仅 weakScore 5 分 |

**代价**：表述不规范的真经历会漏判（「数据质量保障是我的日常」无动作词 → weakScore）。拿不准就 **A/B 对照**：复制一份画像、只给易误报维度加 contextWords，改完跑 `screener.js rescore`（基于本地缓存**零网络**重算）即可对比两版分数差异，确认误报降、漏报可接受后再定主画像。

**适用判断**：容易在自我评价/软技能里被泛泛提及的维度（治理、方法论、意识、能力类）→ 配；硬性事实类（证书、行业名、城市、工具名）→ 不必配（提到就是真提到）。

### evaluationCriteria：精细评估档（LLM）的自然语言标准（v2.6.0）

用户选了精细评估（或当次说「精细评估一下」）时，AI 会话逐份读简历工作内容打分，标准**优先取画像的
`evaluationCriteria` 字段**（一段自然语言），缺席才从 `scoring` 的 rules/weight 推导。**AI 建画像时，
若用户档案偏好为 detailed 或用户提到要精细评估，就顺手生成它**——写法要点：

- 讲清「要什么样的人」：职责、深度要求（做过 ≠ 主导过）、底线项（缺了直接降级）
- 各维度给**评分锚点**：什么样的经历给 80+（S），什么给 60+（A），什么只给弱分——AI 按锚点对齐 gradeBands
- 写「证据要求」：判断依据必须是简历里的具体经历描述，自我评价/求职意向类的表态最多给弱分

```json
"evaluationCriteria": "招数据分析师（偏业务）：①数据治理（30%）：主导过指标体系/数据标准建设的给高分，仅自我评价提及数据质量意识的给弱分；②业绩落地（30%）：有可量化结果（提升X%、覆盖Y条业务线）的给高分；③工具技能（25%）：SQL/BI 平台实际使用经历才算，罗列技能名词不给分；④行业背景（15%）：电商/物流优先。底线：无任何数据项目经历描述的不超过 C。"
```

注意：快速档（规则引擎）不读这个字段，两边互不影响——同一画像可同时服务两种评估方式。

## 四、多岗位并行使用

每个岗位一个画像文件，统一放在 skill 外部的 `profiles/` 目录：

```
<项目根>/
├── liepin-resume-screener/     # skill 工具包（通用，不含岗位数据）
├── boss-resume-screener/       # BOSS 通道（与猎聘共用 profiles/）
└── profiles/                   # 岗位画像（有多少岗位就放多少个）
    ├── _template.json
    ├── example-销售经理.json
    └── <你的岗位>.json
```

运行用 `JOB_PROFILE` 指定（只写 `profiles/xxx.json` 即会自动在「当前目录 → skill 上级目录 → skill 目录」查找），**数据目录按岗位×平台分开**，避免候选池互相污染。

推荐用根目录 run.bat（自动按 `data/<岗位名>/<平台>/` 隔离）；AI 会话内手动跑：

```bash
# 岗位 A · 销售经理
JOB_PROFILE="profiles/销售经理.json" \
SCREENER_DATA_DIR="./data/销售经理/liepin" \
node "<skill目录>/scripts/screener.js"
```

这样各岗位各自有独立的 `processed.json`（防重复请求）、`recommended-index.json`（推荐去重）、简历缓存与配额计数，互不干扰；报告也分别生成。

## 五、新增岗位的标准话术（用户可直接复制）

```
新岗位：<岗位名称>
城市：<城市，可多个>
项目：<项目名>
核心要求：
- 领域经验：<大客户/渠道/某市场…>
- 成果要求：<业绩量化/达标率…>
- 核心技能：<谈判/客户开发/某工具…>
- 行业背景：<目标行业…>
硬性条件：<年龄上限/最低学历…>
加分项：<…>
打招呼卖点：<…>
```

把上面这段填好发出来，AI 会生成对应画像文件并给出运行命令。
